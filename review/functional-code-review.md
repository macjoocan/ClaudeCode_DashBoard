## 상세 발견 사항

### R01 — 종료 대상을 포트·프로젝트로 확정하지 않는다

위치: `Stop.vbs:34`의 2차 종료 루프, `Launch.vbs`의 `FindLauncherProcess`·`StopListener`·`LauncherListener`.

`Launch.vbs`는 `node server.js`로 시작하므로 프로세스 명령줄에 저장소 절대 경로가 없다. `Stop.vbs`의 첫 경로 필터가 실패하면 두 번째 루프가 명령줄에 `server.js`가 있는 **모든** Node 프로세스를 종료한다. 다른 프로젝트의 개발 서버도 해당한다. `Launch.vbs`도 문자열 `server.js`만 검사하고 전달받은 포트를 사용하지 않는다. 다른 서버가 하나만 있어도 런처 프로세스로 오인해 복구 대상으로 잡을 수 있다.

권장: 해당 포트의 리스너 PID를 조회하고, 이 저장소의 절대 스크립트 경로 또는 명시적인 프로세스 식별 기록과 함께 검증한다. 대상이 확정되지 않으면 종료하지 않는다. 검증을 위해 실제 프로세스를 종료하지는 않았다.

### R02 — WebSocket 입력의 JSON 형태와 PTY write 실패를 방어하지 않는다

위치: `terminals.js:attach`의 `message` 콜백과 `write` (`terminals.js:437`).

JSON 파싱만 예외 처리한다. 유효한 JSON인 `null`을 받으면 `m.t`에서 TypeError가 나고, `{"t":"i","d":{}}`를 받으면 객체가 그대로 `proc.write`에 넘어간다. PTY write 자체도 try/catch가 없어 종료 직전의 write 실패가 같은 경로로 빠져나갈 수 있다. 이벤트 콜백 예외가 처리되지 않으면 대시보드 서버 전체가 종료된다.

격리 재현: 실제 `attach`·`write`와 EventEmitter를 사용해 두 메시지 모두 콜백 밖으로 예외가 나오는 것을 확인했다. PTY 타입 검증은 모의 경계로 대체했다.

권장: 객체·메시지 타입·문자열 입력·크기 검증을 하고, PTY write 실패를 해당 연결의 오류로 처리한다.

### R03 — 리다이렉트에서 최초 URL의 프로토콜 모듈을 계속 사용한다

위치: `server.js:726`, 특히 모듈 선택 `server.js:732`와 재귀 `go` 호출.

`http`/`https` 모듈을 최초 URL로 한 번 결정한다. 일반적인 HTTP→HTTPS 리다이렉트 후에도 `http.get(httpsURL)`을 호출해 `ERR_INVALID_PROTOCOL`이 발생한다. 두 번째 호출은 비동기 응답 콜백 안에서 일어나므로 최초 Promise 생성자의 예외 처리 범위를 벗어난다. 파일·이미지 URL을 끌어다 넣는 동작이 서버 종료로 이어질 수 있다.

격리 재현: 실제 `downloadToPaste`에 HTTP 경계만 모의로 붙여 301의 HTTPS Location을 전달했고 콜백 밖 예외를 확인했다. 외부 URL 요청은 하지 않았다.

권장: 각 hop의 `target.protocol`로 모듈을 고르고, 동기 get 실패도 reject로 변환한다.

### R04 — 재시작 대기 중의 터미널 수명과 중복 실행을 검증하지 않는다

위치: `terminals.js:240`의 `restart`, 특히 `wait.then` 이후 spawn.

같은 터미널에 재시작 요청 두 개가 들어오면 둘 다 같은 이전 프로세스의 종료를 기다린 뒤 새 PTY를 하나씩 만든다. 두 번째가 `t.proc`를 덮어써 첫 번째 프로세스가 추적에서 빠진다. 재시작 대기 중 패인을 닫아 Map에서 제거해도 후속 continuation이 PTY를 새로 만든다. 브라우저 탭을 여러 개 열거나 재시작 직후 닫기를 누를 때 발생할 수 있다.

격리 재현: 실제 `restart`에서 동시 요청으로 spawn 2개/등록 1개, 대기 중 close로 spawn 1개/등록 0개를 확인했다. CLI는 실행하지 않았다.

권장: 터미널별 하나의 재시작 작업만 유지하고, await 후 Map의 객체 신원과 취소 상태를 다시 검사한다. 이전 flush·hold 상태도 함께 정리한다.

### R05 — 프로젝트 에이전트의 생성·목록·편집 경로가 서로 다르다

위치: `config-write.js:445`의 `createAgent`, `config-write.js:528`의 `readDoc`, `config-write.js:539`의 `writeDoc`, `public/config-edit.js:454`의 `openEditor`, `harness.js:307`의 에이전트 수집.

생성은 선택한 프로젝트의 `.claude/agents`에 쓰지만, 생성 직후 열리는 편집 요청에는 프로젝트 정보가 없다. 서버 `readDoc`·`writeDoc`도 전역 `AGENTS_DIR`만 사용한다. 전역에 같은 이름이 없으면 성공적으로 만든 에이전트를 편집할 수 없고, 같은 이름이 있으면 그 전역 파일을 열어 저장한다. 구성 목록도 전역 폴더만 훑어서 새 프로젝트 에이전트가 목록에 나타나지 않는다.

권장: 파일의 소속 프로젝트·범위를 목록부터 편집·저장까지 유지하고 서버에서 그 대상 경로를 검증한다. 삭제 요청의 범위도 같은 기준으로 정리한다. 실제 사용자 파일을 만들거나 덮어쓰지 않고 연결된 호출 경로로 확인했다.

### R06 — 플러그인 설정 범위가 정상 CLI 경로에서 빠진다

위치: `config-write.js:642`의 `setPluginEnabled`, `public/config-edit.js:548`.

UI는 `scope`·`cwd`를 보내지만 정상 경로에서는 `claude plugin enable/disable <name>`만 호출한다. 범위와 cwd는 CLI가 실패해 직접 settings를 고치는 fallback에만 쓰인다. 프로젝트 설정 대상을 고르고 플러그인을 변경해도 CLI 기본 대상에 반영되어 선택한 프로젝트 파일과 결과가 달라질 수 있다.

권장: 지원되는 CLI 범위 옵션과 cwd를 명시해 정상 경로와 fallback의 저장 대상을 일치시킨다. CLI의 사용자 설정은 변경하지 않았다.

### R07 — 프로젝트 MCP 설치가 런처의 작업 폴더를 대상으로 실행된다

위치: `config-write.js:555`의 `runClaude`, `config-write.js:591`의 `mcpAdd`, `mcpRemove`, `public/config-edit.js:568`.

MCP 폼은 local/project 범위를 고를 수 있지만 선택한 프로젝트 경로를 넘기지 않는다. `execFile`에도 cwd가 없어 서버의 작업 폴더에서 CLI를 실행한다. 다른 프로젝트의 MCP를 추가하려고 해도 런처 폴더 기준으로 설치된다. 제거도 같은 문제를 가진다.

권장: local/project 범위에 대상 프로젝트를 필수로 받고 cwd를 검증해서 execFile에 전달한다. 목록·연결 상태 확인도 같은 프로젝트 기준으로 맞춘다.

### R08 — SSE 스냅샷에서 완료 매칭에 필요한 ID를 버린다

위치: `events.js:308`·`events.js:309`, `public/live.js`의 `applyToLive`.

실시간 PreToolUse·SubagentStart는 브라우저 상태에 `id`를 넣지만, 새로고침·재접속 때 받는 스냅샷에는 name/type/ms만 있다. 이후 완료 이벤트는 `t.id !== toolUseId`·`a.id !== agentId`로 제거하므로 스냅샷에서 온 항목이 남는다. 완료된 도구가 계속 실행 중으로 표시되고 에이전트 수·흐름 표시도 부풀려진다.

격리 재현: 실제 이벤트 수집기로 스냅샷을 만들고 실제 브라우저 상태 갱신 함수에 완료 이벤트를 넣어 항목이 그대로 남는 것을 확인했다.

권장: 스냅샷과 증분 이벤트에 동일한 ID 필드를 유지한다.

### R09 — 대화 응답을 현재 열린 세션과 다시 대조하지 않는다

위치: `public/index.html:1866`의 `loadTranscript`, 특히 응답 후 `openSess.provider` 참조와 `log.innerHTML` 대입.

세션 A 대화 요청 후 B를 열면, 늦게 도착한 A 응답이 B 패널을 덮어쓴다. 응답 이후 provider 라벨도 전역 `openSess`에서 읽어서 A의 Claude 응답에 B의 Codex 이름이 붙는다. 패널을 닫은 경우에는 null 참조가 catch로 들어가 불필요한 실패 표시도 만든다.

격리 재현: 실제 `loadTranscript`의 fetch만 지연시켜 요청 중 세션을 A→B로 바꿨다. B provider 라벨 아래 A 내용이 렌더링되는 것을 확인했다.

권장: 요청 시작 때 provider/slug/id와 요청 번호를 캡처하고 응답·catch·타이머 적용 전에 현재 패널과 일치하는지 확인한다.

### R10 — Codex 상태 파일의 나이만으로 실행 중을 판정한다

위치: `codex.js:62`의 `liveMap`, `public/index.html:1320`의 `liveBtn`, `public/index.html:1849`.

`liveMap`은 파일이 하루 이내면 PID 생존 여부 없이 실행 상태를 반환한다. 강제 종료 등으로 SessionEnd 훅이 남기지 못한 파일이 있으면 목록은 이어하기 대신 창 띄우기를 표시하고 대화 패널의 이어하기도 숨긴다. 브리지 대상 선택에는 2분 신뢰 규칙이 있지만 목록 버튼에는 적용되지 않아 같은 세션이 기능마다 다르게 판정된다.

권장: PID와 프로세스 신원을 검증하고, 상태의 신뢰도·만료 처리를 브리지와 목록에 공통 적용한다. 코드 경로 확인이며 실제 프로세스를 강제 종료해 시험하지 않았다.

### R11 — 텍스트 입력 요소를 전역 검색 단축키에서 제외하지 않는다

위치: `public/index.html:2491` 부근의 document keydown.

터미널 영역과 검색창만 예외 처리한다. 브리지 메시지 textarea, MCP URL·경로·설정 input에서 `/`를 입력하면 preventDefault 후 검색창으로 포커스가 간다. URL·파일 경로·슬래시 명령 입력이 끊긴다.

권장: input/textarea/select/contenteditable 및 IME 조합 중인 이벤트에서는 전역 검색 단축키를 실행하지 않는다. 문서 편집기 사례는 범위에서 제외했다.

### R12 — 청크 사이의 미완성 JSONL 레코드를 이어 붙이지 않는다

위치: `server.js:242`의 `parseSession`, `eachLine`.

HEAD_MAX까지 넓혀 읽지만 매번 96KB의 독립된 문자열을 파싱한다. 경계에서 잘린 레코드는 첫 조각이 JSON 파싱에 실패하고 다음 조각은 `dropFirstPartial`로 버려진다. 첫 사용자 메시지가 큰 붙여넣기·지시문을 포함하면 제목과 최초 시각이 누락되거나 뒤의 메시지로 바뀐다. 해당 레코드가 tail 표본에도 없으면 복구되지 않는다.

격리 재현: 앞에 cwd 레코드, 150KB 사용자 메시지, 뒤에 충분한 시스템 레코드가 있는 합성 파일로 실제 파서를 실행했다. 유효한 사용자 메시지가 있어도 `firstPrompt`가 null이었다.

권장: 청크마다 마지막 미완성 줄을 보관해 다음 청크와 결합하고 마지막 EOF 레코드를 처리한다. 레코드 길이 제한이 필요하면 별도로 명시한다.

- `public/term.js`: fallback 복사 textarea를 성공·예외 양쪽에서 제거하고 원래 입력 포커스를 복원한다.
- 비동기 복사 완료가 새로운 선택을 지우지 않는다. 복사 단축키는 브라우저 기본 동작을 막아 중복 처리를 줄인다.
- 우클릭을 capture 단계에서 처리해 xterm의 숨은 textarea 이동·선택 경로와 충돌하지 않게 했다. Ctrl+V·Ctrl+Shift+V·Shift+Insert는 기존 네이티브 paste 이벤트를 사용한다.
- Ctrl+A는 커서가 있는 **현재 화면의 프롬프트 표시 텍스트**를 선택한다. Ctrl+Shift+A는 터미널 출력 전체를 선택한다. 도움말도 변경했다.
- 회귀 테스트는 포커스 복원·예외 정리·비동기 선택·기본 이벤트·프롬프트 범위·여러 줄·빈 줄·한글 셀 폭을 확인한다.

선택은 xterm 화면의 복사용 선택이다. CLI 입력 모델의 편집 선택이 아니므로 선택 후 타이핑·Delete로 프롬프트 전체가 교체되지는 않는다. `❯`·`›`·`>` 프롬프트와 화면 경계를 인식하며, 화면 밖으로 숨겨진 입력·접힌 대형 paste·다른 CLI 테마·프롬프트 내부의 독립적인 `>` 줄은 전체 범위를 정확히 추출하지 못할 수 있다. 인식하지 못할 때 출력 전체를 선택하는 fallback은 사용하지 않는다. Claude의 Ctrl+A 기본 의미는 줄 시작 이동이며 이 UI에서 복사용 선택으로 바뀐다. [공식 입력 단축키](https://code.claude.com/docs/en/interactive-mode).

사용자가 겪은 간헐적 증상의 **가능한 코드 원인**을 회귀 테스트로 확인하고 수정했다. 실제 Windows 브라우저·OS 클립보드·실행 중 CLI를 통한 재현과 체감 개선 확인은 수행하지 않았다.

## 검증과 유지할 장점

`node review/functional-review-repros.cjs`는 위 6건의 기존 결함을 격리해서 확인한다. 현재 결함이 존재한다는 assertion이므로 합격 기준 테스트가 아니며 향후 수정 시 해당 assertion도 변경해야 한다. 실제 CLI·외부 URL·사용자 설정은 사용하지 않는다.

전체 기존 테스트와 새 회귀 테스트는 `npm test`로 실행했다. 최종 실행 수치는 `review/test-results.txt`에 남겼다. 문서 기능은 리뷰·수정에서 제외했지만 공용 코드의 회귀를 확인하기 위해 전체 테스트는 실행했다.

기존 구성 쓰기의 백업·임시 파일 재파싱·이름 검증, 삭제의 휴지통 이동, 브리지의 중복 본문 전송 방지·대상 기록 확인, provider별 실행 인자 분리는 유지할 가치가 있다. 현재 테스트가 기본 동작을 넓게 다루고 있지만 위 발견 사항처럼 비동기 경합·재접속·잘못된 경계 입력의 통합 경로는 추가 검증이 필요하다.
